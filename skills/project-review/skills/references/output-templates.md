## プロジェクトレビュー Markdown テンプレート

コンソール出力・ファイル出力のどちらでもベースは同じテンプレート。0 件のセルは `0` のままにし、観点別の指摘リストは「指摘なし ✅」と記載するか省略する。

```markdown
# 🤖 Claude プロジェクトレビュー

- **リポジトリ**: {REPO_ROOT}
- **ブランチ**: {BRANCH}
- **HEAD SHA**: {HEAD_SHA}
- **レビュースコープ**: {REVIEW_SCOPE_DESCRIPTION}  例: `リポジトリ全体（218 ファイル）` / `src/auth/ 配下（42 ファイル）`
- **実行日時**: {YYYY-MM-DD HH:MM}
- **動作確認**: {実施 / 未実施（理由）}

## 📊 概要

**Severity 別件数:**
| 分類 | 件数 |
|------|------|
| 🔴 MUST（修正必須） | X |
| 🟡 SHOULD（修正推奨） | X |
| 🟢 NICE TO HAVE（検討推奨） | X |
| **合計** | **X** |

**観点別件数（11 観点 × severity）:**
| 観点 | 🔴 | 🟡 | 🟢 | 状態 |
|------|----|----|----|------|
| コード正確性 (correctness) | N | N | N | ✅ |
| プロジェクト規約 (conventions) | N | N | N | ✅ |
| パフォーマンス (performance) | N | N | N | ✅ |
| テストカバレッジ (test_coverage) | N | N | N | ✅ |
| セキュリティ (security) | N | N | N | ✅ |
| エラーハンドリング (error_handling) | N | N | N | ✅ |
| 可読性・保守性 (readability) | N | N | N | ✅ |
| シンプル化 (simplify) | N | N | N | ✅ |
| アーキテクチャ・設計 (architecture) | N | N | N | ✅ |
| リポジトリ共通観点 (repo_common) | N | N | N | ✅ / ⏭ 未起動 |
| 重点観点 (focus) | N | N | N | ✅ / ⏭ 未起動 |

- 「状態」列は `✅`（A_i 成功）/ `⚠️ 失敗`（A_i 失敗）/ `⏭ 未起動`（条件未充足）のいずれか。

## 🚨 優先修正候補

最重要 0〜5 件を観点横断で抜粋（MUST / 動作確認失敗のうち、特に対応優先度が高い指摘）。0 件なら「なし ✅」。

例:

1. **[security]** `internal/auth/jwt.go` JWT 検証で `alg=none` を許容しており、署名なしトークンが通る。
2. **[correctness]** `internal/db/migration.go` ロールバック不能なマイグレーション 3 件。デプロイ後のロールバックパスが無い。
3. **[verification]** `go test ./internal/auth/` で `TestAuthorize/unauthenticated_user` が落ちている（200 を返す）。

## 🔁 横断的な傾向

同じパターンが 3 箇所以上で繰り返されている問題を 0〜5 件で要約。0 件なら「なし ✅」。

例:

1. **[performance]** N+1 クエリのパターンが `internal/service/` 配下の 4 ファイルに点在（order, payment, user, notification）。共通の Repository 経由で eager loading に統一を推奨。
2. **[conventions]** `fmt.Println` 直書きが 27 箇所に存在。プロジェクトのロガー (`internal/log`) への置き換えを推奨。
3. **[error_handling]** `err` を握り潰すパターン（`_ = doSomething()`）が 12 箇所。少なくとも warn ログの出力を推奨。

## 🧪 動作確認

| チェック | 結果 | 所要 | 備考 |
|---------|-----|------|------|
| 例: go build ./... | ✅ pass | 15s | - |
| 例: go test ./... | ❌ fail | 62s | TestAuthorize/unauthenticated_user が失敗 |
| 例: golangci-lint run | ✅ pass | 8s | - |
| 例: govulncheck | ⏭ skipped | - | バイナリ未取得のためスキップ |

- **総合**: `✅ 全チェック成功` / `❌ 失敗あり（N 件）` / `⚠️ 一部スキップ`
- **再現コマンド（失敗時）**: 失敗したチェックの再現コマンドと、該当ログファイル（`/tmp/check-*.log`）のパスを記載。
- **スキップしたチェック**: 理由を 1 行で添える。

動作確認を実施できなかった場合は、理由に応じて以下のいずれかを記載する:

- `PROJECT_VERIFY=no`（ユーザーが動作確認をスキップ）: `⏭ 動作確認は未実施（ユーザー選択によりスキップ）`
- subagent B が失敗 / 実行環境エラー等: `⚠️ 動作確認は未実施（理由を記載）`

## 🔎 メタレビュー（観点別 C_i）

| 観点 | overall_quality | invalid | severity 調整 | 文言改善 | 漏れ補完 |
|------|------|---|---|---|---|
| コード正確性 (correctness) | good | 0 | 1 | 0 | 1 |
| セキュリティ (security) | good | 1 | 0 | 1 | 0 |
| ... | ... | ... | ... | ... | ... |
| **合計** | - | N | N | N | N |

- C_i が失敗していた / 起動されなかった観点は `overall_quality` 列を `⚠️ 未適用` と記載する。

## 💬 総評

3〜5 文で記載。以下の 4 要素を必ず含める:

1. **リポジトリ概要 + 良い点**: 各 A_i の `overall_comment` と REPO_STRUCTURE から、リポジトリが何をしているか・良い点を 1〜2 文で要約。
2. **主要リスク**: 「🚨 優先修正候補」から最重要 1〜3 件を抜粋して短く言及。
3. **横断的傾向**: 「🔁 横断的な傾向」から 1〜2 件を抜粋。
4. **観点別品質の偏り**: C_i の `overall_quality` が割れている場合、最も低い観点を 1 つ言及（例: `観点別品質: test_coverage が needs_improvement、その他は good 以上`）。

## 🔴 MUST（修正必須）

該当する指摘がなければ「指摘なし ✅」と記載。ある場合は**観点別カテゴリ**で記載:

### セキュリティ (security)

- **`internal/auth/jwt.go:42`** — JWT 検証で `alg=none` を許容している。
  - 攻撃者が署名なしトークンを送ると認証が通る。`alg=RS256` のような期待値を明示検証する必要がある。
  - 改善方針: `if token.Method.Alg() != "RS256" { return ErrInvalidAlg }` を追加する。

- **`internal/handler/` 配下（user_handler.go / order_handler.go ほか）** — 認可ミドルウェアが適用されていない HTTP ハンドラが 8 件ある。
  - 認証済みであれば誰でも他人のリソースにアクセスできる（IDOR）。
  - 改善方針: ルーティング登録時に `RequireResourceOwner` ミドルウェアを追加する。

### コード正確性 (correctness)

- （該当する指摘。なければこのカテゴリを省略）

### エラーハンドリング (error_handling)

- （該当する指摘。なければこのカテゴリを省略）

### 動作確認 (verification)

- （動作確認 subagent B からの行/ファイル単位の失敗指摘。`PROJECT_VERIFY=yes` で失敗があった場合のみ）

（他観点で MUST がある場合は同形式で追加）
```

## 指摘エントリのフォーマット

各 finding は以下の形式で書き出す。`path:line` または `scope`、severity タグ、本文、改善方針の順。

### 行レベルの指摘

```
- **`path/to/file.go:42`** — <指摘の要点を1文で>
  - <詳細な説明（なぜ問題か、どう影響するか）>
  - 改善方針: <改善内容を 1〜3 文で>
  - （該当する場合のみ）他観点からも該当: `correctness` / `error_handling`
```

### ファイル / ディレクトリ / モジュール単位の指摘

```
- **`path/to/dir/` 配下** — <指摘の要点を1文で>
  - 対象範囲: <scope の内容。代表ファイルパス + 「ほか N ファイル」など>
  - <詳細な説明>
  - 改善方針: <改善内容>
```

### 横断的傾向としてまとめる場合

```
- **[<観点ID>]** <パターンの要約>: <N 箇所>で同じ問題が確認されている。
  - 代表例: `path/to/file1.go:42` / `path/to/file2.go:88` / `path/to/file3.go:120`
  - 改善方針: <共通の改善方針>
```

`fmt.Println` のようにファイル単位での件数情報があるとレビューを進めるユーザーに有益なので、可能なら**ファイル別件数**を併記する:

```
  - ファイル別件数（上位 5 件）:
    - `internal/handler/user_handler.go`: 8 箇所
    - `internal/handler/order_handler.go`: 6 箇所
    - `internal/service/payment.go`: 5 箇所
    - （他 5 ファイル: 計 8 箇所）
```

## コンソール出力時の圧縮ルール

プロジェクト全体レビューは出力が長大になりがちなので、`OUTPUT_TARGETS` にコンソール出力が含まれる場合は以下のルールで圧縮してもよい:

1. **観点別の指摘リスト**: 1 観点あたり MUST > SHOULD > NICE TO HAVE の順で並べ、件数が多い severity は「ファイル別件数表 + 上位 5 件のみ詳細」にする。詳細を省略した分は「他 N 件（詳細はファイル出力 / `/tmp/project_review_subagents_<timestamp>.json` を参照）」と注記する。
2. **「🔁 横断的な傾向」を先頭付近に出す**: コンソールでスクロールしながら読む際、最も価値のある「全体傾向」が先に目に入るようにする。
3. **メタレビュー表は折りたたみ的に短縮**してよい: コンソール出力時は overall_quality だけ列挙し、invalid / severity 調整 / 文言改善 / 漏れ補完 の件数合計のみ示す。観点ごとの内訳が必要ならファイル出力を参照させる。

`OUTPUT_TARGETS=both` の場合は、**ファイル出力は完全版を保ち、コンソール出力のみ圧縮**する。`OUTPUT_TARGETS=console` のみの場合は、圧縮版を出した上で末尾に「完全版が必要なら再実行時に `OUTPUT_TARGETS=file` を選択してください」と添える。

## ファイル出力時の保存ルール

`OUTPUT_TARGETS` にファイル出力が含まれる場合:

- 既定パス: `/tmp/project_review_<YYYYMMDD-HHMM>.md`
- ユーザーが別パスを指定した場合は尊重する。
- **リポジトリ内のパス（`docs/` 配下など）が指定された場合**は、書き込み前に「リポジトリ内に保存しますがよいですか？（Git 追跡対象になります）」と 1 回確認する。
- ファイルが既に存在する場合: 上書き前にユーザーに確認する（既存レポートを誤って消すリスク回避）。
- 書き込み後、コンソールに `保存先: <絶対パス>` を 1 行表示する。

### 副次的なファイル出力

- **subagent の raw 出力ログ**: `/tmp/project_review_subagents_<YYYYMMDD-HHMM>.json` に常に保存する。後からユーザーが C_i の判断や A_i の元データを確認したいときに使う。
- **動作確認ログ**: 個別のチェックログ（`/tmp/check-<name>.log`）は subagent B が書き出す。レポート本文には summary とログパスのみ記載する。
